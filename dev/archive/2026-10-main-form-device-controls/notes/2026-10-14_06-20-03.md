# Verify Devices

Verify on the device: HSTP offset sign and units, whether a running HSSP playback picks up an offset change immediately, offset persistence across device reconnect, how quickly an online player's changes become visible via GET, stroke normalization/rejection behavior, and 200-with-`error` responses.

Do the device-contract checks **before HandySync connects**, because the selected connect policy will reapply HandySync’s saved values and could overwrite the values you’re trying to observe.

1. Use an authenticated API client (such as the official API docs’ “Try it out” flow) and record the date, model, and firmware from `GET /info`. The repo’s API notes link to the authentication guide; don’t put tokens in URLs or logs.
2. Read and save the original values from `GET /hstp/offset` and `GET /slider/stroke`. Also capture `GET /settings/slider` and `GET /capabilities`.
3. **Check offset sign, units, and live effect:** start a known HSSP script alongside video with an identifiable action. Change the offset by a modest amount, such as +250 ms, while playback continues; observe which direction and roughly how far the action shifts. Try the negative value, then check whether it takes effect without restarting playback. Confirm with GET and restore the original value.
4. **Check persistence:** set recognizable but safe offset/stroke values, then check them after a HandySync disconnect/reconnect and, separately, after a device power cycle. Query before reconnecting HandySync so its saved settings don’t mask device persistence. Restore the originals afterward.
5. **Check external-player visibility:** change offset and stroke in an online player, then query the GET endpoints and record how quickly the values appear. Repeat while HandySync is connected once the polling implementation exists.
6. **Check stroke normalization and errors:** try valid stroke values and compare the PUT response with GET. Test boundary or invalid ranges only with playback stopped, and restore the original range. A normal HTTP failure does **not** verify the special HTTP-200-with-`error` case; use a known device condition that produces that response, or record it as unverified and cover parsing with a mocked automated test.

The existing `VERIFICATION.md` lists the results to capture. Some checks, especially HandySync’s poll behavior and UI updates, have to wait until that implementation exists.
