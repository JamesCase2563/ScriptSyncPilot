## Remaining Questions 2026-10-04_13-56-14

Your answers above are recorded in [the design](../DESIGN.md). These questions concern the remaining defaults and implementation details, not the already agreed features.

1. **Merge default:** Should the collision sub-option initially select Keep Existing or Use New when different values share a timestamp?
    * remember the previous collision choice. The initial default isn’t important.
2. **Boundary points:** Should an existing point exactly at the insertion start or end count as a conflict? Proposed: include both boundaries, because generated cycles also have values there.
    * preserve an existing boundary point instead of adding a competing generated point. Omitting the pattern’s first/last point can help, but doesn’t guarantee smooth movement: interpolation may create a long ramp or change the first/last cycle. Preview those transitions; don’t omit endpoints unconditionally.
3. **Suggested cycle count:** When a timeframe is entered, should the tool suggest the nearest positive whole-cycle count from observed cadence, rounded down, or rounded up? The user can override it, and the tool shows the resulting effective cadence.
    * don’t expose rounding options. Automatically suggest the nearest positive whole-cycle count from measured cadence and the selected duration, while allowing direct editing.
   - Benefit: complete cycles fit the timeframe with minimal input.
   - Tradeoff: effective cadence may differ slightly from measured cadence.
4. **Starting-phase choices:** Is starting at the minimum moving up or at the maximum moving down sufficient initially, or should any phase within the cycle be selectable?
    * offer **Continue Existing** and **Pattern Start** initially. Continue Existing uses the interpolated value at insertion time and chooses a compatible phase/direction where possible; otherwise it falls back to Pattern Start. Future editable patterns define their own natural starting point. Put additional phase controls in profile settings.
5. **Profile defaults:** Is a 25% rise / 75% return a suitable initial fast-up/slow-down ratio? Which easing shape should slowed direction changes use, and how accurately should sampled actions approximate it?
    * start with a 25% rise/75% return and cosine easing near direction changes. Use adaptive sampling targeting at most one position-unit deviation, then adjust after trial.
6. **Generation limits:** What should the default maximum section duration be (for example, 3 hours), and how far may users raise it? What maximum generated action count should protect against excessive memory use?
    * duration alone doesn’t predict size; cadence and sampling density matter. An action has two integers, roughly 8 bytes of raw data: 100,000 actions is about 0.8 MB before overhead. Serialized JSON/CSV is larger. I suggest a configurable three-hour section limit and an initial 100,000-action safety cap. These are editor safeguards, **not verified Handy upload limits**.
7. **Undo history:** Should history be limited by number of edits, memory usage, or both? Is there a preferred default? The history representation can be chosen during implementation while preserving multilevel undo/redo and redo clearing on new edits.
    * usually modest with edit deltas, potentially large with whole-document snapshots. A million-action document is roughly 8 MB raw; 100 full snapshots approach 800 MB before overhead. Use deltas for small edits and retain affected sections for bulk edits. We shouldn’t need a restrictive edit-count limit initially.
