# Command Ordering Design

**Status:** M1 characterization complete 2026-11-07; implementation and new verification have not started.
**Affected projects:** HandySync, with Common/mpv session integration only where needed to characterize target replacement.
**Production-readiness priority:** 3, command ordering.

## Goal

Verify that queued or in-flight work cannot issue a stale play/seek/synchronization command after Handy disconnect begins or after the mpv session/Handy client target changes. Preserve serialized device commands and existing lifecycle behavior.

This work verifies the supported lifecycle baseline. Automatic recovery, session restoration, and command coalescing remain deferred.

## Existing baseline and inputs

- HandySync documents a single serialized device-command gate, captured-client identity checks, session transitions, and awaited teardown in [architecture](../../HandySync/ARCHITECTURE.md).
- The archived [timeout-shutdown verification](../../archive/2026-11-timeout-shutdown/VERIFICATION.md) covers disconnect admission, pending writes, in-flight play cancellation, queued seek suppression, late transport completion, gate drain, and deferred teardown.
- The [HandySync backlog](../../HandySync/BACKLOG.md) defers desired-state/coalescing and automatic takeover/recovery. This work must not silently expand either scope.
- Inspect actual current `MainForm` transitions and tests; prior evidence may not cover mpv session replacement while commands are queued/in flight.

## M1.1 Characterization: command producers, captured targets, and gates

Reviewed the current HandySync `MainForm`, its [architecture](../../HandySync/ARCHITECTURE.md), and the focused lifecycle/playback tests. The device-command gate provides serialization; it does not by itself establish that queued work still belongs to the active targets. Stale-target protection comes from the identity, readiness, lifecycle, cancellation, and edit-generation checks described below.

| Producer | Captured target and commands | Gate and lifecycle checks | Existing evidence and boundary |
| --- | --- | --- | --- |
| Connect, reads, and script installation: `ConnectHandyAsync`, `CheckDeviceFirmwareAsync`, `ReadAndAdoptDeviceControlsAsync`, `ReSetupScriptAsync`, `EnsureCurrentScriptInstalledAsync`, `SetupScriptOnDeviceAsync` | Connect captures a `HandyApiClient`; script installation additionally snapshots the `Funscript` reference and `_scriptVersion`. The initial connection requests, firmware/control reads, upload/setup, and replacement stop all target that client. | REST work is serialized through `_deviceCommandGate`; script installation holds it over the stop/upload/setup sequence. Connect and replacement paths check client identity around awaited work. Setup checks script reference/version after upload before issuing HSSP setup. Disconnect first clears `_handy`, cancels pending requests, then drains the gate before stop/disposal. | [`HandyApiTimeoutTests`](../../../tests/ScriptSyncPilot.FunscriptEditor.Tests/HandyApiTimeoutTests.cs) covers connect/upload timeout suppression and [`DeviceControlPollingTests`](../../../tests/ScriptSyncPilot.FunscriptEditor.Tests/DeviceControlPollingTests.cs) `CanceledScriptInstallGateWaitDoesNotReleaseUnownedPermit` covers cancellation while setup waits for the gate. These do not cover every queued connect/setup operation racing a different client or script replacement. |
| Playback and synchronization: mpv position/pause/speed callbacks and `_syncTimer` (`OnMpvPositionChangedAsync`, `OnMpvPauseChangedAsync`, `OnMpvSpeedChanged`, `OnSyncTickAsync`) | Callback methods retain the originating `MpvSession`; play/stop/resync and sync also capture the current `HandyApiClient`. Shutdown cancellation is passed to requests. Those tests do not directly replace a target while its command is queued and then assert that no request is sent. |
| Video transport: waveform seek and play/pause buttons (`SeekMpvAsync`, `SetVideoPausedAsync`) | `SetVideoPausedAsync` snapshots `_mpv` into a local session before sending. `SeekMpvAsync` reads `_mpv` when invoked and sends the waveform seek to that session; these are mpv IPC commands, not Handy commands. | Neither uses `_deviceCommandGate`. Video play/pause guards attachment, no-op state, and pending transport before sending; seek is fire-and-forget from the waveform. Attach/detach uses `_sessionTransitionGate`, and the session's disconnect callback checks it is still `_mpv` before requesting detach. | [`HandySyncErrorReportingTests`](../../../tests/ScriptSyncPilot.FunscriptEditor.Tests/HandySyncErrorReportingTests.cs) covers fixed seek/play/pause failure feedback, and `MpvPlayFailureStatusSurvivesAutomaticDetachAfterPipeDisconnect` covers disconnect callback cleanup. | Offset/stroke writes: slider handlers, `ScheduleOffsetWrite`, `ScheduleStrokeWrite`, and their debounce workers | Each worker captures the current client, the requested value(s), and its own cancellation-source identity. These operations are independent of mpv state. | After the debounce, workers wait on `_deviceCommandGate` and recheck cancellation, support/disconnect state, client identity, and that their cancellation source is still current before sending. | Device polling: timer and form-activation producers (`PollDeviceValuesAsync`, `UpdateTemperatureAsync`) | A poll snapshots the current client and offset/stroke edit versions; temperature reads use the same client. | Polling acquires `_deviceCommandGate` non-blockingly and checks the captured client/lifecycle before and after each request and between endpoints. Disconnect stops the timer and clears poll state before request cancellation; close/disconnect conditions prevent applying late values. | [`DeviceControlPollingTests`](../../../tests/ScriptSyncPilot.FunscriptEditor.Tests/DeviceControlPollingTests.cs) covers polling failure/recovery, preserving local edits, and not polling after disconnect/close. | Attach/detach, Handy disconnect, and close (`AttachMpvAsync`, `DetachMpvAsync`, `DetachMpvCoreAsync`, `DisconnectHandyAsync`, shutdown handlers) | Attach creates and stores a new `MpvSession`; event delegates close over that session. This map distinguishes the command target from the gate that orders it. M1.1 confirms existing disconnect and late-failure coverage, but does not establish the queued mpv-session replacement invariant. M1.3 below records that and other deterministic gaps. This is characterization only, not a claim that every producer/transition pair has been exercised.

## M1.3 Missing deterministic scenarios

M1.1 and M1.2 show that disconnect ordering and late timeout handling have focused evidence, but the session-replacement cases below remain unverified. These are test scenarios, not findings that the current implementation is defective.

| Transition and timing | Deterministic scenario | Expected assertion and current evidence boundary |
| --- | --- | --- |
| mpv replacement while an HSSP callback is queued | Hold `_deviceCommandGate`; start `OnMpvPositionChangedAsync` for session A so its resync waits at the gate; detach A and install session B before releasing the gate. Repeat for queued `OnMpvPauseChangedAsync` and `OnSyncTickAsync`. | Assert no request from A is sent after A is no longer current, and B's readiness/status is unchanged. The handlers recheck identity after acquiring the gate, but existing tests cover disconnect suppression or rate changes, not this replacement ordering. |
| mpv replacement while an old HSSP command is in flight and succeeds | Block a fake HSSP play/stop response after request start, detach A while it is blocked, then release a successful response before teardown completes. Include position-resync play if kept as a separate producer. | Assert the old completion does not log playback/resync success or set a status for B. Existing stale-target tests cover late timeouts/failures; `OnMpvPauseChangedAsync` and `OnMpvPositionChangedAsync` currently continue to success reporting after their awaits without a post-await target check, so this test may expose a defect requiring M2 correction. |
| First sync after mpv replacement | Set a known position on A, attach a playing session B at a different position, and invoke sync before B emits its first position update. | Assert `synctime` cannot use A's `_lastKnownPos`. The field is shared across sessions, and attach does not reset it; no current test characterizes the first sync after replacement. |
| mpv IPC seek during detach/replacement | Start a waveform `SeekMpvAsync` against A with a controlled pipe write, detach/replace A before the operation completes, then complete or fail the old write. | Assert the old operation cannot present a result as belonging to B. Existing form-level seek tests cover failure text, not the operation racing session replacement. This is separate from HSSP seek/resync ordering. |
| Handy client replacement during teardown | Hold a serialized Handy request and attempt reconnect while disconnect is draining or deferred. | Existing lifecycle behavior blocks reconnect until the captured client's gate/requests are drained and teardown completes; archived timeout/shutdown tests cover the deferred case. A separate supported overlap is not currently identified. |

These scenarios define the missing M1 evidence. M2 should prioritize queued callback suppression, stale in-flight success reporting, and first-sync position isolation; the controlled transport should release operations in a fixed order so each assertion is deterministic. |

## Proposed approach

1. Map command producers and the command gate: setup, play/stop, seek, drift correction, offset/stroke writes, polling, disconnect, close, and mpv attach/detach/replacement.
2. Define stale-target cases separately: Handy client disconnect/replacement and mpv session replacement. Identify which commands belong to which captured identities.
3. Use deterministic fake transports and controlled tasks to hold a request while a transition occurs; inspect request order and ensure late completions cannot update the new target's UI/readiness.
4. Reuse timeout-shutdown tests as baseline evidence, then add only missing tests or fixes.
5. Keep the single gate and manual reconnect semantics; do not introduce a new queue policy or recovery controller.

## Invariants to verify

- Commands for one Handy client remain serialized.
- Once disconnect starts, queued writes/play/seek work for that client sends no new request; in-flight work is canceled or safely observed before teardown as defined by the existing lifecycle contract.
- A late completion for a replaced client or mpv session cannot mutate or report success for the current target.
- Transitions do not allow an old mpv session's position/play state to drive a new session's device commands.
- Cleanup retains the client until in-flight work has completed or is safely deferred; no disposal race is introduced.

## Constraints

- Do not add command coalescing, automatic reconnect, takeover detection/restoration, or expanded retry behavior.
- Do not promise physical stop during communication loss.
- Treat session replacement coverage as a verification question; do not assume existing checks cover every transition.

## Completion criteria

- A command/transition matrix documents verified and unverified cases.
- Disconnect and target-replacement races meet the invariants above, with focused automated tests for newly covered behavior.
- Exact evidence and limitations are recorded in [VERIFICATION.md](VERIFICATION.md) and linked to the top-level release gate.
