# Error Message Inventory

**Status:** M1.3 characterized 2026-11-02; updated for M2.1 behavior changes 2026-11-03. This records present behavior; uncovered failures are not claimed safe or tested.

API errors below refer to `HandyApiClient`'s normalized messages: `<operation> failed: <HTTP status>.`, `<operation>: HTTP transport failed[ (<status>)].`, `<operation>: transport I/O failed.`, `<operation>: invalid JSON response.`, `<operation>: invalid response shape.`, `<operation>: response did not contain a result.`, or `<operation>: device error[ <code>].` Response bodies and untrusted device error names/messages are omitted. Timeouts use `<operation>: request timed out.` The form now replaces raw mpv/filesystem exception details with fixed messages on the reviewed paths.

## Characterization boundaries

- `Log` sends messages to both the visible log textbox and persistent `AppLog`; `SetStatus` updates the status label. Some paths only log and leave the status label unchanged.
- Maintainer preference: error and validation feedback should not block the user with modal message boxes; show it in the current form's log, status, or a relevant inline control. M2.1 removed modal error/validation feedback from the reviewed HandySync paths; the file chooser remains a user-initiated dialog, not an error message.
- The most material uncovered cases are ordinary non-timeout form-level Handy failures, actual offset/stroke write failures, mpv attach/video command failures, and repeated temperature-read failure state. M2.1 fixes are not yet covered by focused regression tests.
- The archived credential and timeout records provide the specific evidence linked above. This inventory is not a new test run and does not claim that an untested case passes.
