I recommend organizing by **current project**, with proposed platform work kept separate.

**What Exists**
- `SPEC.md` is a **whole-platform vision**, not a controller-only specification. It describes several projects and capabilities that don’t exist yet.
- **HandySync** currently owns device control and playback synchronization. It is the closest thing to a controller today, but is not the proposed `ControllerHost`.
- **Common** is a shared library containing Funscript handling, mpv IPC, and logging. It is **not a controller**.
- **FunscriptEditor** is the editing application.
- `ControllerHost` and `Core` are proposed projects, absent from `ScriptSyncPilot.slnx`.

**Suggested Structure**
```text
dev/
  README.md                   # Project map and documentation guide
  ARCHITECTURE.md              # Current system and project boundaries
  VISION.md                   # Long-term direction, not implemented spec
  BACKLOG.md                  # Cross-project work only

  HandySync/
    ARCHITECTURE.md            # Current synchronization/device lifecycle
    BACKLOG.md                 # Consolidated improvement proposals

  FunscriptEditor/
    ARCHITECTURE.md            # Timeline, editing, persistence, mpv lifecycle
    BACKLOG.md                 # Pattern insertion and other editor features

  Common/
    ARCHITECTURE.md            # Shared responsibilities and contracts

  proposals/
    ControllerHost.md          # Proposed controller architecture and scope
```

**Document Rules**
- **Architecture:** what exists today, including ownership and important contracts.
- **Vision:** longer-term product goals.
- **Backlog:** future work, with priority and status.
- **Plans:** create only when a backlog item is selected for implementation; keep its tasks in that plan rather than maintaining separate PLAN, TASKS, and ROADMAP documents with overlapping content.

**Proposed Cleanup**
- Rework the existing spec into `VISION.md`, clearly marking speculative components.
- Move pattern insertion from `BACKLOG.md` into the editor backlog.
- Consolidate `IMPROVEMENTS.md` into the HandySync backlog, distinguishing implemented foundations from remaining work.
- Consolidate the controller documents into one proposal. Their task statuses are inconsistent: “project skeleton completed” appears above an unstarted, nonexistent ControllerHost project.
- Replace obsolete paths and project names when migrating.

I would keep **HandySync** named HandySync and **Common** named Common. Introducing a separate controller project should remain an explicit future architectural decision, not something implied by reorganizing documentation.
