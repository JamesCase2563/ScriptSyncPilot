Yes: use a separate folder under the owning project. I’d call these **initiatives** to distinguish them from the actual .NET projects.

```text
dev/
  FunscriptEditor/
    ARCHITECTURE.md
    BACKLOG.md
    work/
      pattern-insertion/
        PLAN.md
        DESIGN.md
        VERIFICATION.md
    archive/
      2026-10-pattern-insertion/
        PLAN.md
        DESIGN.md
        VERIFICATION.md
```

Keep it lightweight:
- **PLAN.md:** scope, decisions still needed, milestones, task checklist, and status.
- **DESIGN.md:** implementation details when substantial enough to deserve a separate document.
- **VERIFICATION.md:** acceptance criteria, test results, and unresolved limitations.
- Add research or experiment notes only when useful.

When the initiative finishes:
1. Update the permanent architecture documentation with the implemented design.
2. Move remaining ideas into the project backlog.
3. Record the outcome and PR reference in the plan.
4. Move the entire initiative folder into `archive/` and update links.

Archived documents are historical snapshots, not maintained instructions. Permanent docs should explain the current system without requiring readers to consult archives.

For work spanning both applications and Common, use `dev/work/` and `dev/archive/`. Otherwise, keep it under the owning application, even when it involves a small Common change.

I’d replace the earlier suggested `plans/` convention with this structure, using one initiative folder per feature rather than per release or PR.
