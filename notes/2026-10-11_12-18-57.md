Besides offset and stroke range, these parts of the v3 API matter for HandySync, roughly in order of value. None of them are in the HandySync backlog yet.

**Worth considering**

1. **Device mode taken over by another app** (`GET /mode`, or `mode_session_id` from `/sids`). This fits your problem with online players best. If a browser player switches the device to another mode or replaces the loaded script, HandySync doesn't notice, because it only sets mode and script when you connect. The polling planned for offset and stroke could also check the device's mode session ID. A change means another app took over, so HandySync should set the mode and script again. This overlaps the backlog's Reconnect and HSSP Recovery item.
2. **Playback speed** (`playback_rate` in `hssp/play`). HandySync always sends 1.0. If you change speed in mpv, the device drifts and the regular time correction keeps fighting it. HandySync could watch mpv's `speed` property and pass it through. This is a separate feature from the editor's playback-speed item, and I think it's the most useful one here.
3. **Device reboot or reconnect detection** (`GET /sids`). The boot and socket session IDs change when the device reboots or reconnects to the server. That tells HandySync when the device's mode, script, and possibly offset and stroke need to be applied again. It belongs to Reconnect and HSSP Recovery and is cheap to include in the same polling.
4. **Time-correction smoothing** (`filter` in `hssp/synctime`). It's fixed at 0.5. Making it configurable could help on unstable Wi-Fi, but I'd only expose it as an advanced or diagnostic option.
5. **Device-to-server clock sync** (`GET /hstp/clocksync`, `GET /hstp/info`). These start a device-to-server clock sync and report the delay between the device and the server. They're useful for the Timing and Diagnostics item, but they're not user settings.

**Read-only, display at most**

- **Physical slider settings** (`GET /settings/slider`): the slider's speed limits and minimum/maximum stroke in mm. The spec says these can only be changed in the Handy onboarding app. They could appear in a tooltip on the stroke slider.
- **Slider state and capabilities** (`/slider/state`, `/capabilities`): motor temperature, and whether the device has a battery and how many sliders. These are diagnostics only; battery level itself comes only from the SSE events below.
- **SSE events** such as `temp_high`, `slider_blocked`, and `battery_changed`. These would be useful warnings once the notification stream is implemented.

**Not relevant**

The other motion protocols (HAMP, HVP vibration, HSP, HDSP, STREAM, HRPP) aren't used for HSSP sync with a video, and `/hamp/stroke` doesn't affect HSSP.
