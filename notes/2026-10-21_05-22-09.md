# Computer movement detection in movies

**having the author point out the relevant movement makes this much more feasible.** We would not need to start by training an AI to understand the entire movie. A guided motion tracker is a practical first step.

The important distinction is:

- **Detecting that pixels moved** is relatively easy.
- **Determining which movement matters, its direction, and how it maps to script positions** requires guidance.

## Recommended author workflow

For each movement section, the author would:

1. **Select a short time range** with one continuous shot.
2. **Draw a box around the moving feature**, ideally something visually distinct.
3. **Indicate the movement axis** by drawing a line—for example, diagonal rather than strictly vertical.
4. **Mark the two extremes** and say which corresponds to the script’s minimum and maximum.
5. Run analysis, preview the suggested curve, and correct or accept it.

If the camera or the whole subject moves, the author could also select a **reference feature**. We would track the movement *relative to that reference*, rather than confusing camera movement with the intended action.

A box alone might be enough to estimate tempo in a simple shot. The axis, extremes, and reference make position tracking substantially more reliable.

## What the computer would do

| Stage | Purpose |
|---|---|
| Decode frames with video timestamps | Analyze the movie independently of playback speed |
| Track features within the selected region | Follow the relevant object between frames |
| Compensate for camera/reference movement | Separate intended movement from unrelated motion |
| Project movement onto the chosen axis | Produce a one-dimensional position curve |
| Filter noise and identify turning points | Recover cycle timing without excessive script points |
| Map into the selected script range | Generate timestamped positions from 0–100 |
| Flag uncertain intervals | Request correction instead of inventing movement |

Established computer-vision techniques—feature tracking, optical flow, and template matching—are suitable starting points. **A trained model or a powerful GPU would not be a prerequisite for the first prototype.**

## What fits ScriptSyncPilot best

Your existing `scripting workflow` already separates movement sections, tempo taps, and pattern generation. That gives us two useful levels:

**1. Assisted tempo detection — my recommended first version**

The author selects a region and a section. The tracker proposes cycle-boundary taps, which the author reviews before generating a pattern.

This replaces much of the repetitive tempo-tapping work without pretending that screen displacement always equals the desired script depth.

**2. Assisted position generation**

With axis and endpoint calibration, the tracker proposes the actual movement curve, including variations in stroke length. This is more capable, but also more sensitive to perspective, obstruction, and tracking drift.

Both should generate **editable suggestions**, with preview and undo—not overwrite existing work automatically or immediately drive the device.

## What we need to add

The editor currently uses mpv for playback; `MpvSession.cs` exchanges playback state and controls, not image frames. We would therefore need:

- A frame-decoding path, likely FFmpeg.
- An annotation preview for selecting regions, axes, and reference points.
- A tracking engine, likely OpenCV through a .NET wrapper.
- A results preview with confidence warnings and correction/reinitialization.
- Integration with the existing timeline and undo behavior.

**VR needs extra care:** analysis should use a stable projection or fixed viewport. Head movement in the displayed VR view must not become scripted movement. Tracking one eye or a fixed dewarped view would be a sensible starting point.

## Limits to expect

This should work best on continuous shots with visible, distinguishable features. Camera cuts, occlusion, blur, changing perspective, and objects leaving the frame will require author intervention. Also, motion toward or away from the camera cannot always be inferred from a simple tracking point.

**My recommendation:** start with one short, author-selected section, a tracking region, a movement axis, and optionally a reference region. Generate proposed tempo taps first. Once that works reliably on representative clips, extend it to calibrated position curves. That is a bounded computer-vision feature rather than an open-ended “understand the whole movie” AI project.
